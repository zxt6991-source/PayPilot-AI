# PayPilot AI 优化方案（AI PM 作品集版）

基于对 zxt6991-source/PayPilot-AI（v0.4，单 commit 5be3d1f）的代码、文档与评测记录的审阅 · 2026-11-21

## 1. 目标与成功标准

**目标：** 把 PayPilot AI 从“能跑通的工程演示”升级为“经得起 AI PM 面试追问的产品作品”。

**为什么现在的版本还不够：** 工程设计扎实（模型不碰数字、证据可追溯、只读授权），但三个关键问题会在面试中被追问：

1. 100% 通过率来自规则解析加写死答案的合成数据，不代表模型能力。
2. 没有任何真实用户或人工评审证据（human_review.csv 只有表头，对照研究“待执行”）。
3. “Agent”主要是固定流水线，缺少对“自主性边界”的产品决策。

**成功标准（6 周后应当能拿出）：**

- 一份真实模型评测报告（含盲测集、成本、延迟、与规则基线的对比）。
- 一份 3–5 人的对照研究结果（含样本局限）。
- 一份自主性阶梯与路线图，明确“现在做什么、不做什么、什么条件下升级”。
- 一版带置信区间的 report-v2，和一个标注为假设的业务价值模型。
- 一个别人 60 秒内能看懂的仓库首页。

## 2. 现状评估

### 值得保留的设计

- 数字全由 SQL 与服务端装配，模型只选意图与动作标签（ADR-001）。
- 证据表、工具调用幂等键、事件先落库再推送、重启恢复。
- 只读数据库角色、严格参数 schema、写入类请求在调用工具前拒绝。
- 诚实的验收记录：明确写出“真实模型效果、人工引用支持率、真实用户效率改善待验证”。
- 评测基础设施可复用：数据切分哈希、独立 SQL 评分、版本对照报告（v0.3 vs v0.4）、bad case 登记。

### 需要补的差距（按对面试的影响排序）

1. **评测循环论证：** 种子数据里答案写死（Android 前 940 条为回跳超时），用例由模板生成，留出集与开发集同题型，“模型”是正则解析器。
2. **无真实模型数据：** 没有 token 成本、含模型的延迟、人工语义评审；约 0.06 秒的 P95 是进程内规则模式的耗时。
3. **无用户证据：** research/protocol.md 仍是“待执行”。
4. **校验层同源：** validate() 用同一个 build() 重算后比对，只能防证据张冠李戴，防不了逻辑错误；模型尚未参与写文字，它的价值还没发挥。
5. **统计深度不足：** 只有 30 笔样本门槛，无置信区间；ANALYZING 总是下钻最低成功率的终端，存在“多重比较”偏差。
6. **检索很浅：** 5 篇文档、16 个关键词的子串匹配。
7. **工程小项：** runtime.execute 的异常分支引用可能未绑定的 r；评测不在 CI 中；仓库只有一个 commit；项目名与其他 PayPilot 项目重名。

## 3. 优化工作包

每个工作包给出目标、做法、产出物、验收标准和预估工时。优先级：P0 必做，P1 强烈建议，P2 可选。

### WP1 真实模型评测与迭代日志（P0，12–16 小时）

**目标：** 把“100% 通过”换成“真实模型相对规则基线的可复现对比”。

**做法：**

1. 先写盲测集，再跑模型：新增 40 条不来自模板的用例——口语化、中英混杂、错别字与简称、否定句（“不看 Android”）、多条件叠加、越权诱导、提示注入（出现在问题里和知识库文本里）。写完立即冻结并记录哈希，不参与调参。
2. 用 LLM_PROVIDER=deepseek 跑 100 + 40 例，同时保留规则基线。记录：意图与筛选解析准确率、预期状态匹配、拒绝类用例的拒绝率、token 用量与实际花费（运行时已记录 model.usage 事件）、含模型的 P50/P95。
3. 先确认 runner 在 deepseek 模式下评分器仍成立：模型的解析结果可能与规则不同，评分应以预期状态与筛选范围为准，而不是依赖规则模式的内部输出。
4. 建立 bad case 分类（解析漏填、误拒绝、漏拒绝、检索未命中、建议不贴切等），至少 20 条，每条写“现象 → 假设 → 改动 → 复测结果”，延续现有 v03_vs_v04 的写法。

**产出物：** evaluation/reports/real-model-v1.md；扩充后的 badcases/register.csv；v0.5 变更记录。

**验收：** 所有数字可用命令复现；盲测集没有被用于调参；报告同时列出模型胜出与失败的类别；规则模式的结果改称“回归测试”，不再叫“准确率”。

### WP2 对照用户研究（P0，12–16 小时，含招募）

**目标：** 用真实的人的数据回答“它是否真的让排查更快更准”。

**做法：** 按 research/protocol.md 执行。

- 参与者：3–5 位有支付、运营或数据分析经验的同事或朋友，匿名记录，事先说明用途；任务只用合成数据，不接触任何公司数据。
- 设计：六个任务（复算总体成功率、核对 Android 失败分母、定位归一化错误码、判断版本关联、解释空样本、追查其他地区主要失败码）；每人分别用“看板 + 文档”与“AI 诊断”完成，顺序交替。
- 度量：完成时间、答案正确率、求助与重试次数、主观难度（1–5）、查看过的证据。
- 同步抽查至少 30 条关键引用，填写 human_review.csv，得出“引用人工支持率”。
- 提前一周发出邀请，招募是这个工作包最常见的延误点。

**产出物：** research/results-v1.md（含原始记录、样本量、局限）；3 条典型用户原话；由此产生的改进清单并入 backlog。

**验收：** 报告中明确写出 n 和不能推广的范围；至少有一条结论来自用户反馈，并反映到了产品改动。

### WP3 自主性阶梯与路线图（P0，6–8 小时）

**目标：** 回答“这个 agent 什么时候可以动手，而不只是说话”。这是把 SHEIN 桌面 Agent 的 ASK / AUTO / YOLO 权限设计迁移到支付场景的地方。

**做法：** 写 docs/autonomy-ladder.md，定义：

- L0 只读看板；L1 诊断加假设（现状）；L2 给出建议动作，人工确认后创建工单或通知；L3 受限执行（需审批，有风控上限）；L4 低风险自动处置（有熔断与回滚）。
- 每一级写明：允许的动作、主要风险、升级所需的准入指标（如建议采纳率、误报率、回滚率）、回退机制。
- 明确“现在只做到 L1，L2 做原型，L3/L4 不做以及原因”。

**产出物：** autonomy-ladder.md；一页路线图图示；README 中的“边界与不做”小节。

**验收：** 每一级都有可度量的准入条件；能说清为什么当前版本不开放写入。

### WP4 指标素养与统计严谨（P1，8–10 小时）

**目标：** 让报告能区分“真实变化”和“噪声”。

**做法：**

- 在 metric_service 中增加比例差的置信区间：Δ = p1 − p2，SE = √(p1(1−p1)/n1 + p2(1−p2)/n2)，95% CI = Δ ± 1.96·SE。以黄金样本为例：−5.8pp，95% CI 约为 [−7.3, −4.3]pp。
- 小样本提示：30 笔、成功率 90% 时，95% 区间约 ±11pp（正态近似）。把门槛的依据写进指标口径文档，或改为同时展示区间。
- 修正下钻偏差：焦点终端的选择要求最小样本并展示各终端区间，避免“从多个候选里挑最低的那个”造成夸大；报告里注明“已比较 k 个分组”。
- 报告升级为 report-v2，同步更新黄金样本和测试，旧版本保留迁移说明。

**产出物：** report-v2 schema、更新后的 metrics-definition.md、新增测试。

**验收：** 黄金场景的区间可由独立 SQL 复算；小样本分群在报告中显示“差异可能是噪声”。

### WP5 业务价值模型（P1，4–6 小时）

**目标：** 用假设驱动的模型回答“值多少钱”，并明确标注为假设。

**做法：** 写 docs/value-model.md，变量：月有效尝试数 N、客单价 A、成功率提升 Δ、排查时长缩短 ΔT、人力成本 C。

- 挽回 GMV ≈ N × Δ × A；注意 GMV 不是收入，还需乘以费率或毛利。
- 纯示意例子（非真实数据）：N = 100 万笔/月，A = 50 美元，Δ = 0.5pp，则挽回 5,000 笔、约 25 万美元 GMV/月。
- 做 Δ 与 N 的敏感性表，并列出最不确定的假设。

**验收：** 文中所有参数均标注为示意或假设；不使用任何公司真实数据。

### WP6 模型叙述与声明级校验（P2，10–14 小时，可选）

**目标：** 让校验层真正发挥作用。

**做法：** 允许模型写 3 句以内的摘要，每句必须带 evidence_ids；校验器检查摘要里出现的数字是否都能在对应证据中找到，无证据的断言一律拒绝。

**度量：** 数字一致率、无证据断言率、拒绝重试次数、额外 token 成本。

**验收：** 在盲测集上给出上述指标，并说明失败时降级为现有的确定性报告。

**说明：** 只有在 WP1、WP2 完成后才做。

### WP7 包装与工程收尾（P1，6–8 小时）

- **README 首屏：** 60 秒演示 GIF、一页产品简介（用户、痛点、核心指标、明确不做什么）、已知限制（单 worker、仅合成数据）。
- **命名：** 避开已有的 PayPilot 项目；候选如 PayDiag、PSR Copilot、PayLens，自行取舍。
- **提交习惯：** 此后一个工作包一个分支，附 CHANGELOG，让历史看得出迭代。
- **CI：** 把规则模式的评测回归加入 CI 并设最低通过线；E2E 可单独触发。
- **小修：** runtime.execute 的异常分支在循环前初始化 r；ANALYZING 对“所有分组成功率为空”的情况做保护。
- **演进说明：** 单 worker 的限制写明，并给出多实例演进思路（任务租约、SKIP LOCKED 抢占）。

## 4. 时间表（约 6 周，每周 8–10 小时）

- 第 1 周：WP1（盲测集加真实模型运行）；同时发出 WP2 的邀请。
- 第 2 周：WP1 收尾（bad case 分析、v0.5）；WP4 开始。
- 第 3–4 周：WP2 执行与整理；WP4 收尾。
- 第 5 周：WP3、WP5。
- 第 6 周：WP7；时间允许再做 WP6。

核心工作包（WP1–WP5、WP7）合计约 48–64 小时。

## 5. 简历与面试产出

### 完成后可以写的要点（方括号为实测值，未完成前不要写）

- 设计“确定性指标 + 证据校验”的支付诊断 Agent：模型只负责意图解析与动作选择，数字与引用由服务端 SQL 装配并校验；写入类请求 10/10 被拒绝。
- 搭建 [n] 例评测体系（含 [m] 例盲测），真实模型相对规则基线的筛选解析准确率 [x]% → [y]%，单次诊断成本 [$]，P95 [s]。
- 对 [k] 位支付/数据同事做对照实验：任务耗时 [a] → [b] 分钟，关键引用人工支持率 [z]%。
- 提出 L0–L4 自主性阶梯与准入指标，明确 L1 上线、L3 的升级门槛。

### 不要这样写

- “准确率 100%”：来自合成数据与规则解析。
- “P95 56 毫秒”：进程内、不含模型。
- 把回归集通过率说成模型能力。

### 面试高频追问与回答要点

1. **Agent 在哪？** 工作流是确定性的，这是有意为之：支付场景不允许模型编数字。模型负责语义（意图、动作选择），自主性随证据和准入指标逐级放开（见阶梯）。
2. **评测集怎么避免过拟合？** 盲测集先写后跑、哈希冻结，不参与调参；规则回归只作为回归测试。
3. **怎么知道它有价值？** 对照研究的耗时与正确率；价值模型的假设与敏感性；并承认样本小。
4. **什么条件可以升到 L3？** 看建议采纳率、误报率、回滚率等准入指标，再加人工审批与风控上限。
5. **你做了哪些取舍？** 不做写入、不做自动路由切换；统计上宁可提示“可能是噪声”也不夸大。

## 6. 风险与约束

- **数据合规：** 一律使用合成数据，不带入任何公司内部的渠道、错误码口径、业务量或金额。
- **用户研究：** 参与者匿名、事先告知用途；样本小，结论写成“初步观察”。
- **夸大风险：** 所有数字注明数据来源（合成、真实模型或人工）。
- **范围蔓延：** WP6 是可选项；时间紧时先保证 WP1–WP3。
- **成本：** 按 token 记录实际花费，不预先承诺金额。

## 0. 先看结论

**本轮目标不是“把 Agent 做得更复杂”，而是把 PayPilot 从工程演示升级为一套能证明 AI 产品经理能力、可在面试中被追问和复核的作品集。**

优先回答五个问题：

1. **为什么做？** 哪类支付分析用户在什么任务上遇到什么问题？有何替代方案？
2. **为什么用 AI？** 哪些步骤需要语义理解，哪些步骤必须使用确定性计算？
3. **为什么这样做？** MVP 范围、权限边界、错误处理和路线图如何取舍？
4. **效果如何证明？** 真实模型对比、用户任务观察、人工证据复核的结果与局限分别是什么？
5. **我贡献了什么？** 清楚区分个人项目中的产品/技术决策与真实工作中的研发协作经历。

### 四周后的最小成功标准

| 维度 | 必须交付 | 判断为完成的标准 |
|---|---|---|
| 产品定义 | 产品机会说明、目标用户与任务、MVP 优先级表、关键产品决策记录 | 能解释为什么先做“支付异常诊断”，不做什么，以及原因 |
| AI 效果 | 真实模型 vs 规则基线报告、冻结的独立测试集、badcase/迭代记录 | 指标有分子分母、样本来源、模型与配置、成本和运行命令；失败如实披露 |
| 用户价值 | 3–5 名相关背景参与者的任务测试（尽可能达到）、匿名研究纪要 | 至少一项产品改动有用户观察/反馈依据；无法招募时如实标记“未验证” |
| 决策边界 | Agent 自主性分级（L0–L4）与升级条件 | 能说清为什么当前只读、什么条件才允许后续执行动作 |
| 商业思维 | 直接价值模型 + 下游价值假设 | 不把诊断功能直接等同于支付成功率/GMV 的提升 |
| 求职展示 | 60 秒演示、清晰 README、8–10 页作品集、简历项目段落、答辩讲稿 | 招聘者 60 秒能理解业务、产品、结果及限制 |

**求职原则：** 不必等项目全部完成再开始投递。第 1 周完成作品介绍和简历初稿后即可小规模投递、收集反馈；第 4 周形成稳定投递版。

## 1. 现状与个人适配性

### 1.1 项目现状（来自原优化方案的审阅记录，非本次重新跑测）

- 版本：原方案审阅基于 **v0.4 / commit `5be3d1f`**；仓库状态可能随之后提交变化。
- 工程基础：FastAPI + PostgreSQL + React/Vite；支付指标由 SQL/服务端负责，模型主要承担意图与动作选择；只读工具、证据引用、权限控制、任务持久化等已有基础。
- 6 类只读工具：`get_payment_metrics`、`compare_payment_periods`、`get_failure_breakdown`、`get_error_distribution`、`get_release_changes`、`search_payment_kb`。
- 测试背景：原方案记载 100 条固定合成案例（开发集 80 / 留出集 20）在**规则模式**下通过；原方案还转述了后端 39 项与浏览器端到端 14 项测试的验收记录，但该次审阅**未独立复现**。
- 未完成验证：真实模型质量与 Token 成本、人工证据支持率、真实目标用户效率改善。
- 已知设计限制：规则解析和模板样本的同源性，固定工作流的自主性边界、检索覆盖较浅、低样本及分组选择造成的统计误判风险。

> 不允许把“100/100 规则回归通过”写成“AI 模型准确率 100%”，也不允许把不含模型的延迟写成实际 AI 诊断响应时间。

### 1.2 你的优势与缺口

| 维度 | 已具备的证据 | 此轮需要补的材料 |
|---|---|---|
| 支付业务理解 | SHEIN 全球支付模块、20+ 地区、多支付方式、SDK 接入标准化 | 用户痛点与真实任务定义；支付问题的业务优先级 |
| Agent 技术理解 | Electron Agent、工具调用、MCP、RAG、权限治理；PayPilot 自研工作流 | **技术选择背后的产品决策与适用边界** |
| 产品方法 | 曾做复杂模块建设、体验与方案抽象 | 用户研究、需求优先级、MVP 范围、用户价值验证 |
| AI 评测 | 规则回归与自动化验证基础 | 独立盲测、真实模型效果、成本、人工复核、badcase 归因 |
| 商业判断 | 支付 SDK 接入成本降低约 60%（原简历所述，面试需有依据） | 诊断效率/质量价值模型；明确归因限制 |
| 企业产品协作 | 技术项目中的团队合作经历 | 挖掘**确实发生过**的需求、对齐、取舍、上线验收案例 |

**定位建议：** 优先面向「跨境支付 / 电商 AI 应用产品经理」「AI Agent 应用产品经理」「企业智能分析/AI 客服产品经理」，而不是一上来竞争要求多年纯产品管理经历的通用平台负责人岗位。

## 2. 产品定义：先补“为什么做”，而不是先加功能

### 2.1 产品机会（待验证的场景假设）

**目标用户（暂定主用户）：** 跨境支付运营/支付数据分析人员。其他角色如研发排障、支付路由策略和风控可作为次级用户，不能未经访谈直接断言其需求相同。

**核心 JTBD（Job to Be Done）：**

> 当某地区或支付方式的成功率下降时，我希望快速确认异常是否真实、在哪些维度集中、有哪些可核查的失败线索，并拿到有出处的下一步排查建议，以便决定是否升级给支付技术/渠道团队。

**用户当前替代方式（待访谈确认）：** 查支付看板 → 选择国家/终端/方式 → 对比两个周期 → 查失败码和版本变更 → 查知识文档 → 整理结论 → 与相关团队沟通。

**产品主张：** PayPilot 不替代支付决策和自动改路由，而是缩短“发现异常 → 提出可信诊断与下一步核查动作”的路径。

**优先选择支付成功率诊断的原因（候选解释，待访谈验证）：**

- 有明确的基础指标和筛选维度，容易形成可验证的任务；
- 需要同时结合结构化数值、维度下钻和知识文本，具备 AI 辅助的潜在增益；
- 只读诊断可控制风险，适合个人作品集阶段；
- 与已有支付行业经验一致，便于在面试中解释业务约束。

### 2.2 为什么使用 AI？

| 子任务 | 建议实现 | 原因与边界 |
|---|---|---|
| 自然语言中的地区、方式、周期、终端等条件提取 | LLM / 规则基线对比 | 体现语义价值；必须校验参数与歧义 |
| 成功率、分母、同比/环比等计算 | SQL / 确定性服务 | 不允许模型凭空生成指标 |
| 按维度下钻、找集中失败点 | 受约束的工具调用 + 服务端规则 | 控制查询范围，避免偏差与越权 |
| 业务文档查找 | 检索工具 + 明示来源 | 文档命中不足时必须明确标注 |
| 生成结论与核查建议 | 证据装配 / 受约束叙述 | 假设与事实分离；未经验证不得写成根因 |
| 执行支付路由切换、退款等写入操作 | **本轮不做** | 风险高，需要授权、审计、回滚和生产准入 |

### 2.3 MVP 优先级表（需根据用户研究修订）

| 能力 | 优先级 | 为什么纳入/不纳入 | 本轮动作 |
|---|---|---|---|
| 指标口径一致、分母可解释 | Must | 可信诊断的前提 | 保留；补说明文档 |
| 按地区/方式/终端/时间范围诊断 | Must | 核心用户任务 | 保留；补用户任务样本 |
| 证据引用与错误码核查 | Must | 支撑可复核结论 | 做人工证据抽查 |
| 参数缺失时澄清 | Must | 防止错误分析 | 增加真实模型和用户测试 |
| 越权写入拒绝、取消与失败提示 | Must | 安全底线 | 列为守护指标 |
| 追问/报告版本回溯 | Should | 支持连续分析 | 测试可用性，按反馈修复 |
| 置信区间与低样本提示 | Should | 避免数据噪声误判 | 本轮先补风险提示及口径；复杂统计实现延后 |
| L2 创建工单/通知原型 | Could | 方便面试表达路线图 | 只做流程图或低保真原型 |
| 自动路由切换/退款执行 | Won't | 风险与授权成本过高 | 明确写入非目标 |
| 多 Agent、大规模模型摘要生成 | Won't | 与本轮求职目标相关度低 | 不投入开发 |

### 2.4 本轮不做的事

不接入真实公司支付数据；不做生产上线；不承诺提高支付成功率；不做真实支付操作或自动改路由；不为了“Agent 感”引入无必要的多 Agent；不以重写架构/扩展检索框架为主要工作；不追求把所有统计模块升级到研究级复杂度。

## 4. 四周行动计划（按周分任务、工时、交付、验收）

### 第 1 周｜定义产品问题 + 准备求职展示（9 小时）

**目标：** 明确谁需要它、为什么需要、MVP 做什么；同时启动用户招募。**不要等第 4 周才整理 README。**

| 任务 | 时间 | 具体操作 | 验收标准 |
|---|---:|---|---|
| 1. 目标用户与业务流程 | 2 h | 在本周 2 h 内优先安排一次 20–30 分钟首访，再写 1 页产品机会说明，分别记录观察与假设；约不到时保留待验证标记 | 能用 90 秒讲清产品机会 |
| 2. MVP 及决策记录 | 2 h | 根据第 2 节形成 Must/Should/Won't 表；写 3 条 ADR（为何只读、为何 SQL 计算、为何先做诊断） | 每条有备选方案、理由、风险 |
| 3. 用户任务与基础指标 | 1 h | 复用 research/protocol.md 的 6 个任务，按首访线索选重点，补评分标准、错误条件和空数据情况 | 任一任务均可人工判定完成/失败 |
| 4. README 首屏与演示 | 2 h | 首页放 1 句话价值定位、适用用户、现有截图和 60 秒演示稿、三步流程、限制说明 | 外部人不看代码可在 60 秒内说出用途 |
| 5. 招募与求职基线 | 2 h | 联系 5–8 位可能参与者；准备知情说明、排期；整理初版简历 PayPilot 条目和 2 个 SHEIN 真实项目复盘提纲 | 至少发出邀请并记录；简历不使用未验证指标 |
| **合计** | **9 h** | | |

**本周交付：**

- `docs/product-opportunity.md`
- MVP 优先级和三项取舍复用 `docs/product-opportunity.md`；指标实现依据见 `docs/decision-records/001-deterministic-metrics.md`
- `research/protocol.md`（含首访、任务与匿名记录模板），实际邀约后填写招募记录
- `README.md` 首屏、演示素材、简历 v0

**第 1 周完成门槛：** 有明确用户画像（即使暂为假设）、6 个可复测任务、三条取舍理由、真实可演示的产品路径；招募已启动。

### 第 2 周｜真实模型对比评测 + 一次决策驱动的迭代（10 小时）

**目标：** 将规则回归从“模型能力展示”中剥离，回答真实模型到底在什么场景更好/更差、代价是多少。

| 任务 | 时间 | 具体操作 | 验收标准 |
|---|---:|---|---|
| 1. 设计独立样本 | 2 h | 在现有 100 条规则回归以外，新写约 20–30 条**非模板化**挑战样本；如时间许可增至 40 条。区分开发调试样本与**冻结盲测集**；记录 SHA-256 | 有题目、预期状态/筛选条件、类别、评分标准、哈希 |
| 2. 核对评分器与运行环境 | 2 h | 先用开发题分别跑规则和真实模型，检查两份逐题归档、哈希和用量；评分以外部预期状态/范围为准，不依赖规则解析内部中间值；固定版本/温度/数据 | 相同输入可重跑；报告注明模型、日期、配置、数据版本 |
| 3. 跑对照并采集成本 | 2 h | 先用开发题对照定位失败；待下一步修复、候选冻结后，再对同一未见集做最终对照；记录正确率、拒绝/误拒绝、有效任务状态、延迟、tokens 和费用 | 有分子分母与原始结果；失败不删除 |
| 4. Badcase 与产品改动 | 3 h | 将全部失败分类；选择 1–2 个具有产品意义的问题设计修复（如澄清交互、否定条件、错误提示）；只在开发集调整 | 每次修改都有“问题→假设→方案→复测结果”；盲测集不参与调参 |
| 5. 写评测结论 | 1 h | 结论明确回答：哪些场景用规则，哪些场景用模型，何时降级或追问 | 有至少 1 个模型胜出案例、1 个失败/局限案例（若实际出现） |
| **合计** | **10 h** | | |

**本周交付：** `evaluation/datasets/manual-challenge-v1.*`、`evaluation/datasets/holdout-v1.sha256`、`evaluation/reports/real-model-v1.md`、`evaluation/badcases/register.csv`、`docs/decisions/ADR-model-vs-rule.md`。

**重要的实验纪律：**

- 原 100 条合成规则样本主要是**回归集**，不作为独立泛化能力的唯一证据。
- 盲测集在模型/方案冻结后才进行最终评估；若已查看盲测失败再针对性修改，则必须另建新的未见集，不能仍称其为“独立盲测结果”。
- 真实模型质量指标和时延必须明确**是否包含网络、检索、工具和报告生成**。P95 样本少时波动很大，应附样本量和分布，不单独以数字夸大性能。
- 可以以 DeepSeek 作为供应商选项，但应以仓库实际配置和可用性为准；不把 API key、日志中的个人信息上传到仓库。

### 第 3 周｜用户任务测试 + 人工引用复核（10 小时）

**目标：** 用观察证据回答产品是否帮助人完成支付排查，而不是仅判断用户是否觉得 AI 有趣。

| 任务 | 时间 | 具体操作 | 验收标准 |
|---|---:|---|---|
| 1. 确认参与者与试运行 | 1 h | 尽可能选 3–5 位有支付/运营/数据经验的参与者；先做一轮任务流程检查 | 有匿名编号、经验背景和知情说明；不保存不必要的个人信息 |
| 2. 执行对照任务 | 4 h | 使用相近难度的任务 A/B 两套材料，对参与者交替使用“看板+文档”与“PayPilot”；采用 AB/BA 顺序平衡，避免重复题记忆效应 | 每人有开始/结束时间、答案、重试、主观难度、主要困难记录 |
| 3. 整理访谈/任务记录 | 2 h | 计算描述性结果，按正确、部分正确、错误、放弃分类；提取匿名反馈 | 写明 n、参与者背景、任务构成和不能推断的范围 |
| 4. 人工证据复核 | 1.5 h | 从真实诊断报告中抽取目标约 30 条关键“结论→证据”关系，独立复核 | `human_review.csv` 每条可回溯；若抽样不足记录实际 n |
| 5. 转为产品决策 | 1.5 h | 汇总至少 3 个问题，按影响/频率/修复成本排序；确定第 4 周要修复的 1 个高价值问题或明确暂不修 | 至少一项决策直接引用观察或访谈记录 |
| **合计** | **10 h** | | |

**本周交付：** `research/results-v1.md`、`research/raw-sessions/`（脱敏保存）、`evaluation/reviews/human_review.csv`、`docs/backlog-prioritized.md`。

**对照研究的限制：**

- 3–5 人是**探索性样本**，可发现可用性问题和提供方向性证据，不足以证明广泛用户群体的效率提升；结果报告应呈现每人结果而不只给平均值。
- 参与者如不是实际支付分析人员，必须标为**替代用户测试**，不能把其结论等同于支付运营人员的真实工作收益。
- 最好做相近复杂度任务的 A/B 版本，并互换顺序；同一题先传统方法后 AI 的对比会受到学习效应影响。
- 不允许访问或展示任何公司内部真实交易记录、客户数据、渠道合同或非公开指标。

**无法招满人员时的降级方案：** 先完成 1–2 次访谈/可用性测试及证据人工复核；报告写“探索性反馈，尚未构成对照研究”。把完整实验留在 Roadmap 中，不编造人数或效果。

### 模板 E｜直接价值模型（禁止把 AI 诊断等同于 GMV 增长）

**优先估算可以直接观察的价值：**

- `月诊断任务数 M`：每月实际需要人工排查的任务量（当前仅可设置假设）。
- 每种方法以全部分配任务为分母，逐项记录正确完成、部分正确、错误、放弃和最终处理状态。两种方法使用同一任务构成与计时边界。
- 记录每题的实际人工投入分钟，合计操作、复核、重试和转人工接手；另记提交到结束的历时，允许人与系统并行。流程结束仍未解决的任务保留在分母并报告。
- 传统方法和 AI 方法每任务平均人工分钟分别为 T0、T1。月度情景工时差 H = M × (T0 − T1) / 60，允许为负。任务难度构成不同时先按类型匹配或加权。
- 月度情景净价值 = H × 单位工时成本 − 同期新增 API、基础设施及维护成本。已进入人工分钟的复核与接手只计一次。
- 价值报告同时展示正确完成数 / 全部分配数、尚未解决数和人工工时差。完成质量下降时，单列损失及未知影响，暂缓给出正向收益结论。

**下游价值必须单独讨论：**

`AI 诊断 → 找到可执行问题 → 人工/系统采取有效措施 → 因果验证 → 支付成功率变化 → 业务收益`。

没有后续处置实验与因果证据，就不能声称 PayPilot 直接提升成功率或挽回 GMV。可以在价值模型中展示假设敏感性，但必须标注为**情景推演，不是实际项目业绩**。

## 6. Agent 自主性路线图（产品决策版）

| 等级 | 能做什么 | 主要风险 | 进入下一阶段的必要条件 | 当前状态 |
|---|---|---|---|---|
| L0 | 静态指标看板与筛选 | 人工查找成本高 | 统一指标口径，完成可复核数据基础 | 已有看板能力 |
| L1 | 只读诊断、提出假设和证据 | 错误归因、误导分析 | 解析/证据/拒绝等指标达到内部设定验收线 | **当前本地 DEMO 对应阶段** |
| L2 | 建议动作，用户确认后创建工单/通知 | 错误建议产生协作噪音 | 用户确认机制、工单权限、审计及建议质量 | **仅考虑原型，不宣称上线** |
| L3 | 经审批执行受限动作 | 改动真实业务配置的损失 | 权限分级、沙箱/仿真、审批、阈值、回滚、值守 | 本轮不做 |
| L4 | 极低风险场景的自动处置 | 连锁错误、不可逆后果 | 长期生产验证、熔断/回滚、风险责任界定 | 本轮不做 |

**口头说明：** 支付诊断是高风险决策支持场景；模型可以帮助理解用户意图，但财务/支付数值仍由确定性服务计算。权限自主性必须由可追溯数据、可审核动作和明确责任界定逐级提升，而不是为了展示 Agent 能力直接开放生产写入。

### 7.4 从真实工作中提炼 2 个 STAR 故事

**故事 1：全球支付列表跨端重构**

- **S（场景）：** 多终端支付列表有哪些真实问题？来自哪些用户/业务反馈？
- **T（任务）：** 你被要求解决哪些目标，哪些是你建议加入的目标？
- **A（行动）：** 如何和产品/支付研发/测试协作？优先级、组件边界、兼容性如何取舍？
- **R（结果）：** 有何客观证据证明体验/效率变化？没有指标时只写可证明的交付范围。

**故事 2：支付 SDK 标准化接入**

- **S：** 原接入流程哪里重复、成本高？
- **T：** 谁提出需求，你负责什么？
- **A：** 如何定义接入规范、处理不同支付方式的差异，如何与协作方对齐？
- **R：** 原简历中的“接入成本降低约 60%”如何计算（人日、代码量、平均周期等）？准备口径和证据，不清楚则改为保守描述。

> 这两个故事的目的是证明真实企业环境下的需求理解、沟通和交付能力。**只写确实做过的事情**，不把研发协作自动解释为曾任产品负责人。

## 8. 面试高频追问：标准思路（不要背没有发生过的数据）

1. **为什么做支付异常诊断，不做智能客服？** 说明支付业务经验、可衡量任务、可验证证据，以及与其他场景的优先级取舍；承认场景机会仍需用户验证。
2. **这算 Agent 吗？** 系统包含状态管理和受限工具调用，但自主范围经过产品设计刻意限制；不要将固定工作流描述成高度自治 Agent。
3. **为什么模型不算成功率？** 支付统计指标需要统一口径和可复核计算；模型承担语义任务，用证据约束生成结论。
4. **如何证明 LLM 优于规则？** 展示同口径对照、非模板化独立样本和失败类别；若模型没有提升，就说明哪些场景继续采用规则或需要澄清。
5. **怎么避免评测过拟合？** 预设评分规则、冻结独立测试集、留出集不用于调参、记录模型版本和配置。
6. **为什么只招 3–5 人？** 是探索性可用性研究，不是统计上可推广的效果实验；展示用户差异和后续验证计划。
7. **如何衡量商业价值？** 先看正确完成的诊断任务、时间节省、证据质量与单次成本，再审慎分析其可能带来的后续业务收益。
8. **如果可以接入生产支付数据，会先做什么？** 答数据权限、指标口径、脱敏审计、灰度、小流量验证、人工审批与回滚，不直接承诺上线。
9. **你做过哪些真正的产品决策？** 给出备选方案、权衡、用户/评测证据和调整前后对比，而不是只介绍组件实现。
10. **你没有正式 PM title，为什么适合？** 清楚说明支付业务理解、Agent 产品原型与验证能力、真实跨角色协作经验，同时承认仍需要补足规模化产品运营经验。

## 9. 项目风险、合规与真实性规则

| 风险 | 可能发生的情况 | 约束/应对 |
|---|---|---|
| 企业数据泄露 | 把 SHEIN 真实交易、渠道、错误码/费率、业务量写入公开仓库 | 所有演示均使用合成数据；不得泄露内部指标、合同、用户记录、未经授权代码 |
| 数据来源混淆 | 把合成样本/规则回归写成线上模型成绩 | 每一个关键数字标注 `合成 / 规则 / 真实 LLM / 人工 / 假设` |
| 研究误导 | 朋友不懂支付却被描述为支付专家；人数过少得出普遍效果 | 匿名记录真实背景、实际样本量、研究局限及替代参与者比例 |
| 测试泄漏 | 盲测集用于调参或看过题后声称独立 | 冻结并哈希；泄漏后重新准备未见集 |
| 统计误判 | 随机小样本波动、只挑最低成功率分组 | 附样本数与分母；添加“可能为噪声”提示；不夸大根因 |
| API 费用/稳定性 | 模型评测反复调用、超预算、配置失效 | 设支出上限、批量运行前小样本检查、记录失败与重试成本 |
| 面试诚信 | 扩大个人在企业项目中的 PM 职责 | 明确“工程岗位中承担的需求与协作活动”，不编造 PM title |
| 进度膨胀 | 时间被 CI、后端重构和模型摘要占据 | 以简历、作品集和可验证研究优先；高复杂度功能留给下一版本 |
